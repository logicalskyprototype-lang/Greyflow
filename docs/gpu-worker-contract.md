
# GreyFlow GPU Worker Contract

## Purpose

GreyFlow separates request management from GPU-based model execution.

The GreyFlow API handles authentication, validation, job tracking, and
customer-facing responses. A separate GPU worker loads and runs the models.

Kaggle is for experiments only. Production workers must run on infrastructure
that supports persistent services and GPU workloads.

## Architecture

- GreyFlow API: validates and authorizes generation requests.
- GPU worker: executes approved generation jobs.
- Image model: Stable Diffusion 1.5 for the initial implementation.
- Video model: Wan 2.1 1.3B, using a separate video-generation workflow.
- Storage: retains completed outputs and provides controlled download access.

## Worker authentication

Every worker request must use server-to-server authentication.

- Store worker credentials in environment variables or a secrets manager.
- Never expose worker credentials in browser code.
- Reject missing or invalid credentials.
- Do not accept a model path, arbitrary URL, shell command, or executable code
  supplied by a customer.
- Do not trust a job's claimed payment status; GreyFlow verifies payment.

## Image generation contract

### Request

`POST /v1/worker/images`

Headers:

- `Authorization: Bearer <worker-secret>`
- `Content-Type: application/json`

Body:

```json
{
  "job_id": "server-generated-job-id",
  "prompt": "A cinematic coastal landscape at sunset",
  "width": 512,
  "height": 512,
  "steps": 25,
  "seed": 12345
}
```

The job ID must be generated by GreyFlow. Validate dimensions, inference steps,
prompt length, and resource limits before running the model.

The seed may be omitted to allow random generation.

### Successful response

```json
{
  "job_id": "server-generated-job-id",
  "status": "completed",
  "content_type": "image/png",
  "output": {
    "storage_key": "generated/server-generated-job-id.png"
  }
}
```

The storage key is an internal reference, not a public download URL. GreyFlow
controls access to the generated file.

## Video generation contract

Video generation uses a separate endpoint:

`POST /v1/worker/videos`

The request includes a job ID, prompt, validated dimensions, frame count, and
seed. The worker uses the configured Wan model and returns a video storage key.

Video jobs must have separate resource limits and timeout policies because
they are substantially more expensive to execute than image jobs.

## Job lifecycle

The intended lifecycle is:

`queued -> running -> completed`

A failed job transitions to `failed`. Retries must be limited and must not
charge a customer twice.

GreyFlow should persist job state and return a job identifier to the client.
Long-running video generation must not depend on an open browser connection.

## Reliability and security

- Apply request size and generation limits.
- Use bounded concurrency to prevent GPU memory exhaustion.
- Set worker timeouts and handle worker failures.
- Do not log API keys, payment credentials, or full private customer data.
- Verify output files exist before marking a job completed.
- Record model name, duration, status, and resource usage for cost tracking.
- Never mark a job paid or completed based only on a client-side message.

## Implementation order

1. Define and test the image worker interface.
2. Implement a minimal Stable Diffusion worker on suitable GPU infrastructure.
3. Connect GreyFlow to the worker using server-side authentication.
4. Test successful generation, invalid credentials, timeouts, and worker errors.
5. Add the separate Wan video worker.
6. Add durable job queues, storage, payment verification, quotas, and usage
   accounting before accepting paid production traffic.

This document defines the intended contract. It does not mean that a GPU worker,
queue, storage system, or payment integration has already been deployed.
